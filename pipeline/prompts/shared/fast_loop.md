## How to work: fast and aggressive

You run unattended and the gates judge you. Move like a performance engineer, not a committee: make bold structural changes early, leave micro-tweaks for last, and stop when the gates and benchmarks say done.

1. **Edit, then `quick_check`.** Run it after every edit (seconds: incremental build, the query's tests, the differential on the small subset). It covers the full tier's suite, thread counts and a projection of each write kind's cost to the full dataset; fix what it reports, including a projected-cost failure (a write that rebuilds state), before anything else.
2. **Write your own tools, freely.** Throwaway tests, micro-benchmarks, phase timers, visited-state counters, randomized brute-force stress tests, probe programs, ASAN/TSAN runs, gdb on a crash: whatever gets you to a correct state with a large speedup. Put them in `scratch/<name>.cpp` (or `tests/agent_<name>.cpp`) under the query directory: each gets the target `agent_<bench>_q<N>_<name>` automatically (built on request only, never by the gates), and you pass it to `quick_check(targets=[...])`. `scratch/` is yours alone: no gate or audit reads it. `eval/bench/driver/read_latency.hpp` times the engine's SQL against the accelerator over random bindings and prints both medians. Always know your read speed against the engine's own SQL and against the stateless kernel. Keep backups of the variants you tried, revert what does not help, and aim for orders of magnitude on reads, not percent tweaks. The frozen suite and the gates still decide acceptance; your tests are for iterating fast.
   After touching concurrent code (`ParallelEach`, `ParallelReduce`, `PartitionedBuild`, shared state, atomics), run `quick_check(sanitizer="thread", threads=N)`: an instrumented incremental build, the same tests and differential with every phase at N threads; a race with a frame in your query directory fails it (use `sanitizer="address"` for memory errors). `aux_tsan` stays the acceptance gate.
3. **Measure before you hypothesize.** `run_profile` on the CURRENT tree; a digest is stale after any accept or restore. Use `perf` on the bench binary for where the time goes.
4. **Direction, then acceptance.** `run_quick_benchmark` gives direction in seconds. Where the stage asks for an A/B, keep a change only after `begin_ab_trial`, the edit, `run_quick_benchmark(acceptance=True)`, then `end_ab_trial(keep=True)`; otherwise the orchestrator's verdict decides. Compare to `scoreboard.best_valid_score`. A regression is dropped, not shipped.
5. **Gates are for acceptance.** The heavy aux gates are refused until `quick_check` has passed on the current code; request each once after that. `request_gate(name, background=True)` starts a gate while you keep working; read it once with `gate_status`, never in a loop. A failed gate is a fix signal, not a stop.
6. **Scale.** The subset and SF1 are for correctness and direction. Design for SF3000 and never tune against the subset.
7. **Custom profiling.** Add temporary timers and counters, gated on `ACCEL_AUX_CUSTOM_PROFILE` (stateful) or `ACCEL_BENCH_PROFILE` (stateless) and a no-op when unset (`profiling_conventions.md`).
8. **Wall-budget notices on tool results are real.** When one says wrap up, leave the tree building and finish the step.
9. **Never investigate pipeline, gate or orchestrator code to work around a failure.** If the failure is not in your files, call `report_blocker` with the evidence.
